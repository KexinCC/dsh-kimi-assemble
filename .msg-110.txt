feat(1.1.0): verified actions, page state, and diff reads

The extension's click is a DOM-level dispatch: it returns success even when
nothing happens, so a wrong click looked identical to a right one. Every
mutating browser tool now reports whether the page actually changed.

Verified against a controlled A/B with 1.0.1 (6 fixtures x 5 runs, oracles are
machine-checked, see bench/RESULTS.md): task success 37% -> 100%, silent
failures 10 -> 0. The price is one observation window (~600ms) on actions that
genuinely do nothing; normal paths stay within noise of the ~360ms navigate
floor that the extension itself imposes.

- clicks/fills/act verbs capture a page fingerprint before the action and poll
  afterwards (geometric 100/200/400ms inside browserVerifyMs), returning
  changed plus what changed; a stale ref is re-read and retried once and a
  still-failing call returns a fresh snapshot instead of looping
- native dialogs are a state, not an error: click/fill/act answer dialogOpen
  and point at kimi_browser_dialog (plus probeDialog when the observation
  itself was blocked)
- new tools: kimi_browser_act (press/type/clear/select/check/uncheck/hover/
  scroll/drag/mouse_click/upload), kimi_browser_wait, kimi_browser_eval,
  kimi_browser_dialog — 10 capabilities that were previously only reachable
  through raw daemon actions
- kimi_browser_read gains the page-state line (url/readyState/scroll/focus/
  element counts), mode=diff (~4% of the full payload) and include_screenshot;
  snapshot, meta and screenshot are issued in parallel
- kimi_browser_open waits for load by default and drops the extra list_tabs
  round trip (the title comes from the same probe)
- config: browserVerify (auto|off, off reproduces 1.0.x exactly), browserVerifyMs,
  browserReadIncludeMeta
- bench/: fixture server with machine-checkable oracles, self-test, semantic
  checks and the A/B driver, so the numbers above can be reproduced

Waiting deserves a note: the daemon's own wait took 2993ms for a 1.2s render and
evaluate's await-Promise path has ~1s of fixed overhead (both measured), so the
text wait is client-side polling over a DOM walk that skips script/style -- using
textContent matched literals inside inline scripts (a real false positive this
caught).
